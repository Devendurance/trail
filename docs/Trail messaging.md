# Trail messaging

This file turns the approved strategy into product language, UX copy and pitch-ready messages. It intentionally excludes the visual identity direction section from the seven-things scope.

The supplied brief describes a concept product. Use the status labels below when publishing claims:

- **Shipped:** evidenced as implemented and exercised. None is evidenced in the supplied brief.
- **Target:** part of the intended first release.
- **Roadmap:** deliberately deferred.
- **Hypothesis:** requires real-user or market validation.

## Message control

Lead with the human action. Explain the chain, wallet or contract only when it helps the user understand the action or its evidence. Never use a planned feature as proof that the product already works.

## Category and boundary

**Trail is an evidence-labeled app discovery product for firsthand feedback.**

It is not a general wallet, exchange, custody service or universal solution. It performs the narrow action described in the target first release.

## Core message

Trail helps people discover BOT Chain apps through reviews linked to qualifying real use.

## Value proposition

Trail gives discovery more context by attaching a short review to a qualifying on-chain action.

**For the user:** People feel better prepared because they can see a real experience without being told that the app is automatically safe.

**For the surrounding community:** Reviewers contribute useful field knowledge. Builders receive friction reports that popularity metrics do not reveal.

**Why believe it:** The target flow checks chain, receipt, sender, target and eligible event or action, then lets the user sign a bounded authorization for one review. The public page can show the review, outcome tag, explorer evidence and support label.

## Messaging house

### Roof

Trail gives discovery more context by attaching a short review to a qualifying on-chain action.

### Pillar 1: a clear human action

Tell the user what to do in ordinary language. Do not ask them to understand the whole network before they can understand the first step.

### Pillar 2: a visible result

Show the receipt, review state, evidence label or next action that follows the product event. Do not flatten pending, confirmed, verified, reviewed and unresolved into one word.

### Pillar 3: an honest boundary

Make the product's limit easy to repeat. The product should say what its evidence supports and what it does not support.

## Short pitch

Trail helps people discover BOT Chain apps through reviews linked to qualifying real use. It keeps the proof visible and the claim limited to what the product actually checked.

## Full narrative

People currently face this problem: a directory shows what exists and a popularity vote shows who has supporters. Neither necessarily shows whether someone used a specific app or where the experience became difficult. The usual workaround creates a gap between what happened and what another person can understand. Trail closes that gap through a narrow product action, a clear state model and a public result. The product verifies a narrow use event for a curated set of supported apps. It does not certify safety, quality, audits, trustworthiness or universal transaction history. The product is useful only if it tells the truth about its own evidence, so the first release must show both the result and the boundary.

## Feature-to-value translations

- **Wallet connection and network check** → Trail knows which network and account are active → the user avoids submitting proof from the wrong context → the action feels deliberate.
- **Qualifying-use proof rule** → Trail can enforce the defined boundary → the reviewer knows what the review is based on → the product feels dependable.
- **State-specific result** → Trail shows what happened and what remains unknown → the user avoids duplicate submissions → the product reduces anxiety.
- **Public review and evidence page** → another person can inspect the relevant action and reference → the user can decide whether to try the official app → discovery becomes easier to share.

## Voice rules

### 1. Start with the action

Say what the user can do before naming the infrastructure.

- Before: "Access a next-generation on-chain experience."
- After: "Open the app, complete the supported action and submit the transaction hash."

### 2. Show the evidence boundary

Name the exact thing a transaction or review proves.

- Before: "This makes the project trustworthy."
- After: "This confirms the qualifying action. It does not rate the app's safety."

### 3. Be warm without becoming vague

Use the emotional register of the product, but keep the user’s next action visible.

- Before: "A delightful experience for the future of value."
- After: "This review is tied to a verified use event."

## Cadence and sentence rules

- Use short sentences for actions and errors.
- Put the important noun near the verb: app, action, wallet, review, evidence, receipt.
- Use one claim per sentence.
- Keep technical terms in supporting copy unless the user must act on them.
- Do not use a slogan where a label is required.

## Vocabulary bank

Prefer: app, use, review, support, evidence, action, friction, pending, confirmed, unresolved, receipt, explorer.

Use carefully: verified, real, secure, trusted, complete, successful. Add the object and scope whenever one of these words appears.

Avoid: seamless, revolutionary, frictionless, trustless, guaranteed, safe, audited, best, universal, instant, autonomous, yield, alpha, moon, ecosystem solution.

## Product language

### First-use introduction

- **Title:** Verified-use app discovery
- **Body:** Trail helps people discover BOT Chain apps through reviews linked to qualifying real use.
- **Primary action:** Get started
- **Secondary action:** See how it works

### Confirmation before signing

- **Title:** Review before you sign
- **Body:** Check the network, wallet, supported action and review scope before approving this action.
- **Action:** Approve in wallet
- **Secondary action:** Cancel

### Pending

- **Title:** Waiting for confirmation
- **Body:** Your wallet has sent the request. Do not repeat the action while the result is unresolved.

### Rejected

- **Title:** Nothing was confirmed
- **Body:** The wallet rejected the request. Review the details and try again when you are ready.
- **Action:** Try again

### Failed

- **Title:** The action failed
- **Body:** The network did not confirm this action. Check the details before retrying.
- **Action:** Review and retry

### Confirmed

- **Title:** Confirmed
- **Body:** The qualifying action is confirmed. Open the evidence page to see the transaction and support label.
- **Action:** View evidence

### Unknown outcome

- **Title:** We are still checking
- **Body:** We do not know the final result yet. Do not resend. Check the transaction reference or try again after reconciliation.

### Review eligible

- **Title:** Your use is verified
- **Body:** The qualifying action is confirmed. Add what worked or caused friction, then submit one review.
- **Action:** Write a review

### Review published

- **Title:** Review published
- **Body:** Your review is linked to the qualifying action and its explorer evidence. It does not certify the app's safety or quality.
- **Action:** View evidence

### Review unresolved

- **Title:** We could not confirm the use
- **Body:** Keep the review as a draft while Trail checks the transaction, wallet match and supported action. Do not submit another proof transaction.

## Objection responses

### "Is this custodial?"

The intended flow uses connected wallets and a target contract or verification boundary. The product should not describe itself as custody unless the implementation genuinely holds or controls user assets.

### "Does this prove the other side is safe or trustworthy?"

No. The product should state exactly what it checked. A transaction or qualifying action can support a narrow event claim without proving quality, safety, bias or future performance.

### "What happens if the transaction fails?"

The product keeps the failed state separate from confirmation, explains the next safe action and avoids telling the user to repeat an unresolved transaction.

## Tagline system

- **Primary tagline:** Follow the use trail.
- **Supporting line:** See what was actually tried before you connect.
- **Internal trueline:** Popularity without evidence, directories without experience and reviews that imply more proof than they contain.

The tagline carries memory. The one-line description carries clarity. Do not make the tagline do the category’s full explanatory job.

## Claims and proof matrix

- **Claim:** The product supports the narrow action. **Status:** Target until deployed and exercised. **Proof required:** Public working interface and complete transaction or verification trace.
- **Claim:** The result is confirmed. **Status:** Shipped only after the relevant chain state confirms it. **Proof required:** Transaction reference, event or equivalent product evidence.
- **Claim:** Users want this repeatedly. **Status:** Hypothesis. **Proof required:** Repeated real use, not stated interest alone.
- **Claim:** The product improves the wider BOT Chain ecosystem. **Status:** Hypothesis. **Proof required:** Measured discovery, repeat use or builder feedback.

## Testing plan

Test the language with people who are not familiar with the source brief.

1. Ask a stranger to explain what Trail does after reading the first screen.
2. Ask which action they would take next.
3. Ask what the product proves and what it does not prove.
4. Test the pending and failure language with a wallet user.
5. Compare the primary headline with the one-line description and remove any version that sounds like a generic crypto product.

**Acceptance criteria:** A new user can name the category, first action, result and evidence boundary without reading the full page.
